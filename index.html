scheduler中的NodeResourcesFit实现

本文将介绍下Kubernetes中的NodeResourcesFit调度插件的实现。

基本介绍

NodeResourcesFit插件是基于节点资源的调度插件，除了支持节点资源的过滤之外，还支持LeastAllocated(最少资源优先)、MostAllocated（最多资源优先）、 RequestedToCapacityRatio（基于请求量与容量的比率）多个节点优选策略。

实现

预选

节点的预选主要是在Filter阶段实现，这里先在PreFilter阶段计算了Pod的请求量并保存下来，以便在Filter阶段不需要重复计算。

PreFilter

在PreFilter函数中，主要是调用了computePodResourceRequest函数计算Pod的资源请求量，并保存在cycleState中。

Filter

在Filter函数中，首先调用getPreFilterState函数从cycleState取出Pod的资源请求量，然后调用fitsRequest函数计算出节点nodeInfo上不满足的资源量。fitsRequest函数中主要判断了以下条件是否满足：

  1. 判断节点上的Pod数量是否超过限制
  2. 判断节点上的CPU是否满足请求
  3. 判断节点上的Memory是否满足请求
  4. 判断节点上的EphemeralStorage是否满足请求
  5. 判断节点上除了被忽略之外的扩展资源是否满足请求

打分

节点的优选主要是在Score阶段实现，首先在PreScore阶段计算Pod的资源请求量，然后在Score阶段根据不同策略来对节点进度打分。

PreScore

PreScore函数里调用calculatePodResourceRequestList函数获取Pod的资源使用量。calculatePodResourceRequestList函数按照配置的资源依次调用calculatePodResourceRequest函数将资源数量保存在podRequests数组中并保存在cycleState中。

Score

Score函数中首先调用getPreScoreState函数获取Pod的资源请求量。然后调用score函数给节点打分。score函数中对所有的资源依次调用calculateResourceAllocatableRequest计算节点的可分配总量和已分配量，并传递给scorer打分。calculateResourceAllocatableRequest函数用于计算指定节点上特定资源的可分配总量和已分配总量。

这里介绍下LeastAllocated的scorer的实现。在leastResourceScorer函数中，先调用leastRequestedScore函数根据剩余量和总量的比例作为资源得分，并根据资源的权重，计算出最终节点的得分。

总结

本文主要介绍了下用于节点资源过滤和优选的调度插件NodeResourcesFit的实现。

kubernetes中的scheduling-framework介绍

本文将介绍下Kubernetes中的调度框架（Scheduling Framework），Scheduling Framework是一种用于Kubernetes调度器的插件化架构。

基本介绍

Scheduling Framework定义了一些扩展点，调度插件可以通过这些扩展点来实现调度功能。

每个Pod的调度分为调度周期（scheduling cycle）和绑定周期(binding cycle)两个阶段。调度周期用于给Pod选择一个节点。绑定周期用于将调度结果应用到集群中。一个调度周期和绑定周期被称为调度上下文（scheduling context）。调度周期是串行调用的，而绑定周期可能并行运行。

下图显示了一个Pod的调度上下文以及调度接口。

扩展点

PreEnqueue

PreEnqueue接口在Pod加入到内部的active队列之前调用，只有当所有插件都返回Success时，Pod才会放到active队列中。通常用于避免不满足要求的Pod进入调度阶段，从而减少不必要的开销。

触发条件：在Pod进入调度队列之前

返回状态：

状态码 描述
Success 所有插件都返回成功时，Pod放入active队列。
Error 不再继续后续的调度。

EnqueueExtensions

EnqueueExtensions接口用于在集群状态发生变化时，控制是否重新调度被插件拒绝的Pod。通常实现了PreEnqueue、PreFilter、Filter、Reserve或Permit的插件需要实现此接口。

QueueingHintFn

QueueingHintFn是一个回调函数，可以决定Pod是否可以重新放入active队列或者backoff队列。

QueueSort

QueueSort接口用于给调度队列中的Pod排序。注意调度器只能使能一个排序插件。

PreFilter

PreFilter接口用于预处理Pod的信息，如果PreFilter接口返回错误，调度周期会终止。

触发条件：在Pod进入调度周期后

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一阶段。
Error 预过滤错误，结束当前阶段。
Unschedulable 预过滤拒绝，继续调用其他插件。
UnschedulableAndUnresolvable 预过滤拒绝，结束当前阶段。
Skip 跳过后续的Filter阶段。

Filter

Filter接口用于过滤掉Pod无法运行的节点。调度器会针对每个节点，依次按照插件配置顺序调用，如果任意一个插件拒绝，剩下的插件不会继续调用。多个节点的过滤可能并行。

触发条件：在所有PreFilter调用成功后

返回状态：

状态码 描述
Success 通过所有插件过滤的节点为备选节点。
Error 过滤错误，结束当前阶段。
Unschedulable 过滤拒绝，不再进行其他插件的调用。
UnschedulableAndUnresolvable 过滤拒绝，不再进行其他插件的调用。
Pending 过滤拒绝，不再进行其他插件的调用。

PostFilter

PostFilter在Filter接口调用之后，但是只有在没有可用节点的情况下会调用。插件会按照配置顺序调用，如果有一个插件返回Schedulable，剩下的插件不会继续调用。一般PostFilter接口用于实现抢占功能。

触发条件：Pod没有可调度的节点

返回状态：

状态码 描述
Success 有一个插件返回成功后，结束当前阶段。
Error 后过滤错误，结束当前阶段。
Unschedulable 继续下一个插件调用。
UnschedulableAndUnresolvable 后过滤拒绝，结束当前阶段。
Pending 继续下一个插件调用。

PreScore

PreScore接口在打分阶段之前调用，通常用于为打分插件生成共享的数据。如果PreScore接口返回错误，调度周期就终止了。

触发条件：Filter阶段成功执行后

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一个阶段。
Error 结束当前阶段，不再调用其他插件。
Skip 跳过后续Score阶段调用。

Score

Score接口用于给过滤后的节点打分。调度器通过调用各个打分插件，最终生成一个指定范围内的分数。在NormalizeScore阶段，调度器会根据各个插件的权重计算出最终的得分。

触发条件：所有PreScore插件调用成功

返回状态：

状态码 描述
Success 所有插件都执行成功后，进入下一阶段。
Error 打分错误，结束当前阶段。

NormalizeScore

NormalizeScore接口用于在调度器计算节点最终得分前进行分数归一化。

触发条件：在Pod进入active队列之前

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一阶段。
Error 分数归一化错误，结束当前阶段。

Reserve

Reserve接口分为Reserve和Unreserve两个方法，Reserve接口在选好节点后用于预留资源，Unreserve会在预留资源的Pod被拒绝时或者在调用预留插件过程中出现错误时被调用。

触发条件：在选择好调度节点后

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一阶段。
Error 预留错误，结束当前阶段。
Unschedulable 预留拒绝，结束当前阶段。
UnschedulableAndUnresolvable 预留拒绝，结束当前阶段。
Pending 预留拒绝，结束当前阶段。

Permit

Permit阶段通常在调度周期的最后阶段调用，用于阻止或者延迟绑定候选节点。Premit插件有3种结果，approve表示Pod进入绑定阶段，deny表示Pod重新回到调度队列。wait表示Pod处于等待状态。

触发条件：在进入绑定周期前调用

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一阶段。
Error 准入错误，结束当前阶段。
Wait 进入等待状态，需要其他插件没有拒绝。
Unschedulable 准入拒绝，结束当前阶段。
UnschedulableAndUnresolvable 准入拒绝，结束当前阶段。
Pending 准入拒绝，结束当前阶段。

PreBind

PreBind接口用于执行绑定前的动作。例如可以执行网络/存储的准备动作。如果任意的插件返回失败，Pod就会被拒绝。

触发条件：进入绑定周期时调用

返回状态：

状态码 描述
Success 所有插件都返回成功时，进入下一阶段。
Error 预绑定错误，结束当前阶段。
Unschedulable 预绑定拒绝，结束当前阶段。
UnschedulableAndUnresolvable 预绑定拒绝，结束当前阶段。
Pending 预绑定拒绝，结束当前阶段。

Bind

Bind接口用于将Pod绑定到节点上，绑定插件会按照配置顺序依次调用，插件可以选择是否处理，如果有一个插件处理了，剩下的插件都会被跳过。

触发条件：所有PreBind插件都调用成功

返回状态：

状态码 描述
Success 只要有一个插件成功时，就进入下一阶段。
Error 绑定错误，结束当前阶段。
Unschedulable 绑定被拒绝，结束当前阶段。
UnschedulableAndUnresolvable 绑定被拒绝，结束当前阶段。
Skip 当前插件不处理，继续调用其他插件处理。
Pending 绑定被拒绝，结束当前阶段。

PostBind

PostBind接口在Pod绑定节点成功后执行，通常用于清理相关的状态或资源。

触发条件：在Pod绑定成功后调用

返回状态：无

总结

本文介绍了下Scheduling Framework中常见的扩展点，后续再介绍下基于这些扩展点如何实现特定的调度功能。

kubernetes中节点上的设备拓扑亲和

之前的文章介绍了kubelet和device-plugin之间的交互机制，从之前的文章可以发现kubelet在分配设备之前会先计算亲和性，本文将介绍下kubelet中设备拓扑亲和性相关的机制。

基本介绍

工作流程

首先大致看下kubelet中topogoly manager的工作流程。

  1. Kubelet收到Pod创建请求后，调用Topology Manager来判断Pod是否允许准入。
  2. Topology Manager依次调用CPU Manager，Device Manager, Memory Manager来获取Topology Hints。并计算得到最佳Topology Hint。
  3. Topology Manager返回准入成功后，开始调用上述Manager来分配资源。
  4. 分配资源成功后，Kubelet开始创建并启动容器。

scope

目前Topology Manager支持以下几种作用域。

作用域 描述
container 默认作用域，以container为单位进行拓扑计算。
pod 以pod为单位进行拓扑计算。

policy

目前Topology Manager支持以下几种分配策略。

策略 描述
none 默认策略，不执行任何拓扑对齐。
best-effort 尝试寻找最佳的NUMA节点对齐，如果没有找到，仍会调度Pod
restricted 尝试寻找最佳的NUMA节点对齐，如果没有找到，会拒绝Pod
single-numa-node 要求所有资源必须来自同一个NUMA节点，如果不满足，会拒绝Pod

代码分析

直接从calculateAffinity函数入手，首先调用了accumulateProvidersHints函数获取了所有的亲和提示，然后调用对应策略的Merge函数来获取最佳亲和配置。

accumulateProvidersHints函数中调用了所有hintProviders的GetTopologyHints函数，然后把结果保存到数组。

设备的亲和提示实现在devicemanager中。

  1. 首先调用了UpdateAllocatedDevices函数用于更新已分配的设备列表。
  2. 然后调用getContainerDeviceRequest函数获取所有设备资源的请求数量。
  3. 调用deviceHasTopologyAlignment函数判断设备是否支持NUMANode拓扑。
  4. 调用containerDevices函数获取当前容器已分配的设备信息allocated。如果大于0，说明之前已经分配，用allocated重新生成拓扑。
  5. 调用getAvailableDevices函数获取可用的设备available。
  6. 最后调用generateDeviceTopologyHints函数生成设备拓扑提示。

generateDeviceTopologyHints函数中，主要逻辑是遍历所有NUMA组合，根据设备拓扑计算出满足的亲和提示列表。

  1. 首先根据NUMA节点进行组合遍历，比如有0，1两个NUMA节点，那么会遍历 01，10，11三种情况。
  2. 在遍历NUMA组合时，计算出满足NUMA亲和条件的最少的NUMA节点数量minAffinitySize。
  3. 在遍历NUMA组合的同时遍历设备，判断当前设备的NUMA是否落在遍历组合上，如果满足，累加numMatching，直到numMatching大于等于设备请求数量request后，将该种遍历组合保存到亲和提示hints中。
  4. 最后遍历所有满足的hints，如果hint中的NUMA数量和minAffinitySize相等，把hint中的Preferred设置为true。

然后看下Merge函数的实现，这里以best-effort策略为例。首先调用了filterProvidersHints函数来过滤，然后调用Merge函数来得到bestHint。

filterProvidersHints函数里遍历所有的providersHints，将不同资源的hints合并到allProviderHints数组。

Merge函数里，遍历上面过滤后的所有TopologyHints的组合情况，然后调用mergePermutation函数处理每种组合，最后通过compare函数比较获得最佳拓扑亲和bestHint。

mergePermutation函数里遍历了所有的TopologyHints,并将NUMA亲和保存到numaAffinities中，然后取所有numaAffinities的交集mergedAffinity。另外只有所有的TopologyHint都是最优时，最终mergedAffinity才是最优的。

compare函数用于比较两种TopologyHint哪种更优，这里实际情况比较复杂，先不具体介绍了。

CompareNUMAAffinityMasks函数中默认选择占用NUMA节点最少的TopologyHint。

然后再介绍下filterByAffinity函数，因为在这里会根据上面计算出的最佳拓扑亲和来选择设备。

  1. 遍历所有可用设备列表available，并根据NUMA分类保存到perNodeDevices中。
  2. 将所有的NUMA的编号保存到nodes数组中，并按照node是否在最佳拓扑亲和中对数组进行排序。
  3. 遍历所有可用设备列表available和所有的NUMA节点nodes，如果设备没有NUMA信息，保存到withoutTopology中，如果设备的NUMA满足最佳拓扑亲和加入到fromAffinity中，否则加入到notFromAffinity。

总结

本文介绍了kubelet中设备拓扑亲和性相关的机制，主要是拓扑管理器调用各个管理器来获取拓扑提示，然后计算出最佳的拓扑提示，最后管理器在分配时可以根据最佳拓扑来选择资源分配。

kubernetes中的设备分配

之前的文章介绍了在kubernetes中如何实现一个设备插件，本文将结合kubernetes的代码，分析下kubelet和device-plugin之间的交互机制。

基本介绍

首先看下kubelet和device-plugin的整体交互流程。大概分为以下几个步骤：

  1. device-plugin通过gRPC方式调用Register将插件注册到kubelet上。
  2. kubelet调用GetDevicePluginOptions查看device-plugin支持的选项。
  3. kubelet调用ListAndWatch从device-plugin中获取到可用的设备列表。
  4. 当有Pod申请设备时，kubelet先调用GetPreferedAllocation接口获取最优的设备选择。
  5. 然后调用Allocate函数分配设备。
  6. 在容器启动前，kubelet会调用PreStartContainer来初始化设备。

实现

接下来从接口的具体实现看下kubelet和设备插件的交互流程。

Register

先看下Register函数的实现，首先判断了插件版本的兼容情况，然后判断了资源名称是否符合要求，最后调用connectClient函数连接插件。

GetDevicePluginOptions

首先看下GetDevicePluginOptions函数的大致调用流程。

在client的Connect函数中，先和插件的socket建立连接并保存，然后调用PluginConnected函数。

PluginConnected函数中先调用了GetDevicePluginOptions函数，然后将返回的信息保存在endpoints中。

ListAndWatch

先大致看下ListAndWatch函数的调用流程，主要是在pluginManager的Run函数中判断插件需要注册后，启动协程来注册。

在client的Run函数中，首先调用了设备插件的ListAndWatch函数，然后将Recv函数接收到的response，通过PluginListAndWatchReceiver函数处理。

PluginListAndWatchReceiver函数里调用了genericDeviceUpdateCallback函数来处理。

genericDeviceUpdateCallback函数中主要是将设备信息更新到healthyDevices中保存起来，以便后续分配时使用。

Allocate

设备的分配是在Admit阶段进行的，Admit分为Pod级别和容器级别，这里以容器级别的Admit为入口介绍。

Admit函数先调用了calculateAffinity函数计算最佳亲和性，然后调用setTopologyHints函数将最佳亲和配置保存起来，最后调用allocateAlignedResources函数给容器分配资源。

allocateAlignedResources函数中会调用不同的hintProvider来分配，常见的包括cpuManager，memoryManager，deviceManager这些。这里介绍下deviceManager。

继续看下deviceManager中Allocate的实现，主要是调用了allocateContainerResources函数来分配。

allocateContainerResources函数里主要是先调用了devicesToAllocate函数来选择待分配的设备，接着调用allocate函数来调用设备插件的Allocate函数来进行设备的分配。

devicesToAllocate函数中资源的选择逻辑大致如下：

  1. 首先查询容器当前已分配的设备数量，计算得到需要申请的设备数量needed。
  2. 先尝试从可重用的设备分配。如果分配完成，则直接结束。
  3. 然后根据健康设备列表和已经分配的设备计算出可用的设备列表available。
  4. 然后对available调用filterByAffinity函数按照亲和性分类，将可分配的设备分为aligned，unaligned，noAffinity三类。
  5. 如果needed小于aligned，则先调用callGetPreferredAllocationIfAvailable获取设备侧的最优分配preferred，然后和aligned取交集，先从交集中分配，如果分配不足，继续从aligned中分配。如果还是没有分配完成，则报错退出。
  6. 如果needed大于等于aligned，先从aligned中分配，如果分配还没有完成，继续调用callGetPreferredAllocationIfAvailable函数从preferred中分配。
  7. 如果分配还未完成，继续从unaligned中分配。
  8. 最后尝试从noAffinity中分配。

GetPreferredAllocation

在callGetPreferredAllocationIfAvailable函数中，首先会判断插件是否支持GetPreferredAllocation接口，在支持的情况下，会在getPreferredAllocation函数中调用插件的接口来获取设备的最优分配。这里需要注意的一点是available和mustInclude是按照无序列表传参的。

PreStartContainer

PreStartContainer函数的大致调用流程如下，主要是在容器创建之前调用PreStartContainer函数。

callPreStartContainerIfNeeded函数里主要是先查询容器已分配的所有设备作为参数，最后调用插件的PreStartContainer函数。

总结

本文介绍了下kubelet和设备插件的交互流程，主要介绍了下各个接口的调用时机和部分实现。

containerd中CDI的实现

本文将介绍下CDI规范的基本定义，以及在containerd中是如何实现CDI的支持的。

CDI规范

首先我们简单看下CDI规范定义的结构。Spec结构里包含了Version和Kind这些常用信息，Kind用来体现设备厂商和设备类别信息。Devices就是包含了当前所有可分配的设备。

Device结构中有Name字段用于表示设备的名称，便于后续设备分配时使用。

ContainerEdits结构主要描述了需要对容器执行的操作，比如环境遍历的注入，设备节点的创建，挂载点的配置或者是Hook的配置等。

DeviceNode结构里主要是定义了待挂载设备的主机路径、容器内路径，类型和权限等信息。

其余的结构这里不一一介绍了。整体看CDI定义的Spec并不算复杂，主要分为两层，一个是所有设备通用的配置，保存在Spec.ContainerEdits中，一个是具体设备的配置，保存在Spec.Devices中。如果之前了解过OCI规范，就会发现大部分字段定义和OCI规范中的类似。

containerd中的实现

我们以2.1.0版本的containerd代码为例，分析下containerd中是如何支持CDI的。

首先我们通过查找CDIDevice结构发现主要是在WithCDI函数中使用。WithCDI函数接受annotations和CDIDevices两个参数用于获取CDI设备的信息。WithCDI函数返回了一个函数。然后我们看下函数里的处理逻辑，首先遍历了CDIDevices并将设备名称保存到devices切片中。然后调用ParseAnnotations从annotations中解析设备，将解析出来的设备同样保存到devices切片中，最后调用WithCDIDevices函数处理。

继续看WithCDIDevices函数的实现，这里主要是刷新了下缓存，然后调用InjectDevices函数处理。

直接看Cache的InjectDevices函数的实现，核心是遍历设备列表从缓存中取出对应的设备信息，然后合并到一个ContainerEdits中，最后调用Apply函数在ociSpec上应用。

看下Apply函数的具体实现，主要是按照环境变量、设备节点、挂载点、Hook这个顺序将ContainerEdits中的信息转为oci.Spec中的结构并在spec上修改。这样就可以把CDI设备应用到对应的容器上了。

kubernetes中scheduler-extender的实现

本文将介绍下kubernetes调度器中的extender机制，以及如何实现一个基于设备拓扑的extender插件。

基本介绍

什么是extender

在kubernetes中是由调度器来决定Pod最终在哪个节点上运行的。如果想要自定义调度行为，通常有以下几种方式。第一种是直接修改调度器的源码并重新编译运行。第二种方式是自己实现一个调度器，第三种方式是实现extender插件，原生调度器可以通过调用该插件来影响最终的调度结果。extender机制目前提供了3个扩展点，一个是filter阶段用于过滤节点，这个阶段可以过滤掉不满足要求的节点，一个是prioritize阶段，这个阶段用于给满足要求的节点打分，通过分数来描述不同节点的优先程度，调度器最终会根据打分以及不同插件的权重计算出最终的得分，最终选择得分最高的节点调度。还有一个是bind阶段，这个阶段用于把Pod绑定到最终的节点上，绑定之后，对应节点上的kubelet会检测到该调度事件并在节点上运行该Pod。

为什么有extender

上面提到了自定义调度器的几种方式，extender机制相比前两种方式具有以下几个优势，一个是对原生调度器没有侵入式修改，不需要适配不同版本的调度器代码，一个是可以天然集成原生调度器的能力。但是由于extender目前只提供了3个基础的扩展点，因此不太适合实现一些逻辑复杂的高级调度机制。此外，由于extender是以web server + http的方式提供接口，在调度Pod时存在一定时延，在规模较大时可能存在性能问题。目前社区已经提供了新的scheduling-framework机制用于扩展调度器行为，后续我们再做介绍。

实现

调度器配置

首先看下注册extender需要的配置，最核心的配置包括实现extender的web server的地址，以及实现filter和prioritize等接口的URL路径，还有插件的权重。

示例的调度器配置如下。

filter

filter阶段的实现逻辑比较简单，这个阶段的目标是为了过滤掉不满足的节点。我们首先遍历所有节点上的设备拓扑注解，并计算出节点上当前设备的可用数量，然后和Pod请求的设备数量做比较，如果满足则加入到最终满足条件的节点列表中。

prioritize

prioritize阶段主要是通过一定规则给节点打分，最终挑选出最合适的节点。这个阶段我们根据节点的可用设备信息以及Pod申请的设备数量给节点打分，并把最终的分数标准化后返回给调度器。

打分的逻辑在Score函数中实现，首先是根据剩余的设备拓扑以及申请的设备数量，遍历得到可能的分配组合。然后从这些组合中选择出分数最高的分配方式，并返回最高的分数作为节点的分数。

分数的标准化主要是将原先的分数转换成用百分制表示的分数，方便后续的比较和处理。NormalizeScore函数会先找到列表中分数最高的分数，并把最高分作为分母，然后把所有的分数按比例转换为用百分制表示的分数。

bind

bind阶段的实现也比较简单，主要是把Pod绑定到对应的节点上，在这个阶段可以做一些资源的准备动作。

验证

首先我们用kind搭建了一个有2个worker节点的集群，并且每个worker节点上有8个 example.om/demo 设备，并且分为两组。

然后创建带有3个 example.om/demo 设备的pod。此时依旧调度到了k8s-cluster-worker节点。

之后再创建带有3个 example.om/demo 设备的pod。此时调度到了k8s-cluster-worker2节点。因为此时k8s-cluster-worker2节点相比k8s-cluster-worker节点具有更高的分数。

从日志上也可以佐证，虽然k8s-cluster-worker2节点和k8s-cluster-worker节点都满足调度的基本要求，但是k8s-cluster-worker2节点上因为可以把3个设备放入到一个组内，而k8s-cluster-worker节点上3个设备必须分散到两个组，所以k8s-cluster-worker2节点的分数更高。

基本介绍

调度器在给Pod选择节点时，会根据节点上的CPU、内存等不同维度的信息对节点进行打分，最终选择得分最高的节点调度。那么从设备角度而言，目前只能根据device-plugin注册到kubernetes集群中的设备数量信息进行节点打分，为了更好的利用节点内设备的互联拓扑，我们使用device-plugin把设备的拓扑信息呈现在节点的注解中，这样调度器可以使用该信息作出更合适的节点选择。

在PreStartContainer接口中调用updateDeviceZone用于在pod启动前更新设备信息。

在Informer的DeleteFunc中调用updateDeviceZone用于在pod删除后更新设备信息。

kubernetes中的device-plugin的节点内优先分配

本文将介绍下kubernetes中的device-plugin如何使用GetPreferredAllocation接口来实现节点内设备的优先分配。

基本介绍

什么是节点内优先分配

前面的文章介绍了device-plugin负责节点内设备的分配工作，而设备的的优先分配指的是在分配时可以让某些设备被优先分配使用。

为什么需要优先分配

在实际场景中，即使是相同型号的设备，由于设备之间可能存在的互联关系，或者因为设备和CPU存在的物理拓扑关系，导致不同的设备分配组合对应用存在差异。 以NVIDIA的GPU设备为例，由于部分设备之间存在互联拓扑，因此任意两个设备之间的通信并不是完全相同的，比如0号GPU和1号GPU之间有NVLink，而0号GPU和4号GPU之间没有NVLink，那么如果一个任务要申请2个GPU，分配0号和1号的使用效果要好于0号和4号GPU。因此需要使用优先分配机制来根据物理拓扑等条件来选择出最合适的设备列表。

实现

接下来看下在device-plugin中如何实现节点内设备的优先分配。首先看下官方提供的GetPreferredAllocation接口，该接口可以让device-plugin返回一个优先使用的设备列表，我们也是使用该接口来达到设备优先分配的效果。这里我们将设备分成两个组，优先分配的逻辑是尽可能将请求的设备分配到一个组内。需要注意的是，kubelet中的devicemanager并不一定会将该返回结果作为最终的分配结果。

首先需要先在GetDevicePluginOptions接口中设置GetPreferredAllocationAvailable选项。以便GetPreferredAllocation接口能够被正常调用。

然后看下GetPreferredAllocation的实现，我们这里实现的比较简单，使用封装的PerferedAllocate函数来获取优先分配的设备列表，然后设置到对应的ContainerPreferredAllocationResponse中。这里说明下，请求中的AvailableDeviceIDs表示当前可用的设备列表，MustIncludeDeviceIDs表示必须包含的设备列表，AllocationSize表示该次请求申请的设备数量。

PerferedAllocate函数主要分为三步，第一步是根据当前可用的设备列表并扣除必须包含的设备列表，计算出每个组剩余可分配的设备列表，第二步是根据申请的数量以及当前每组可用的设备列表计算出可能的组合情况，并计算每种组合的得分，找到最优的分配组合，最后一步是从可用的列表中按照最优分配选择出最终的设备列表。

GetAvailableZone函数首先根据现有设备的拓扑分组，并计算每组剩余可分配的设备列表。目前构造的分组逻辑是0-3号设备为一组，4-7号设备为一组。然后根据设备的ID和分组的ID对结果进行排序。

GenCombinations函数主要是根据不同分组剩余的资源情况以及资源的申请量计算出可能的组合情况。

getBestAllocate函数用于对分配组合打分，选出分数最高的分配组合。这里使用阶乘来体现同一组内使用的数量越多得分比重越高。

pickDeviceInZone函数用于从当前的分组中按照指定的分配组合获取最终的设备列表。

验证

然后我们来验证下上述的分配策略是否生效。目前我们构造了8个 example.om/demo 设备。并且按照4个一组，将设备分为两组。即0-3号设备为一组，4-7号设备为一组。

我们首先申请了一个example.om/demo 设备，此时分配的是DEMO-4，然后再申请4个example.om/demo 设备，此时分配的是DEMO-0,DEMO-1,DEMO-2,DEMO-3。说明第二个pod分配的设备是在独立的一个组中。

总结

本文简单介绍了下如何使用GetPreferredAllocation来实现节点内设备的优先分配。该功能一般在设备之间存在特定拓扑结构的场景下使用。后续将会介绍如何实现节点间设备的优先分配。

kubernetes中的device-plugin的基本介绍

本文将介绍下kubernetes中device plugin机制，以及如何实现一个简单的设备插件。

基本介绍

什么是device plugin

device plugin是kubernetes官方提供的一种设备插件机制，用于支持不同的厂商注册各自设备到kubernetes集群。

为什么需要device plugin

由于不同的场景需求，用户在kubernetes集群中可能需要使用不同类型的设备，比如GPU设备，网卡设备等。而这些不同类型的设备一般由不同的厂商设计实现，不便直接集成到kubernetes中。因此kubernetes官方设计了一种设备插件机制，用于对接不同厂商的设备。kubernetes官方通过定义统一的设备插件框架，规范了设备使用的方式，也降低了设备接入kubernetes集群的难度。

插件注册

首先我们先进行了设备插件的初始化。初始化主要分为两个步骤，第一步是启动grpc服务端用于提供DevicePlugin接口服务。第二步是连接kubelet并把grpc server注册到kubelet中。

设备列表

设备注册之后，kubelet会调用设备插件的ListAndWatch接口用于获取设备的列表和状态。同时设备插件可以持续监控设备的状态并上报给kubelet。kubelet会根据健康状态来决定更新节点的可用资源。这里简单的构造了设备列表用做示例。

设备分配
